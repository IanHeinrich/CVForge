# 7.5 — Template gallery and region data

## Context

Both pickers are `Wrap`s of `ChoiceChip` over two options each. The
expected growth is **10–15 templates** and **5–6 regions** — two very
different numbers, and they pull the two pickers in opposite directions.

**Templates are chosen by name, with no picture.** "Compact" versus
"Classic Centered" tells you nothing about what you will get. A template
is a visual artefact and the picker shows no visual. At fifteen
templates it is an unordered wall of chips describing documents you
cannot see. `CvTemplate` has `id`, `displayName`, `description`,
`tokens`, `sectionOrder`, `buildDocument` — and no way to show one.

**Regions do not need much.** Five or six is small enough that the chips
would still work; they only stop working because 7.4's document bar is
one row and six chips will not fit in it. So this is a *layout*
constraint, not a scale one, and the answer is a plain dropdown rather
than anything searchable. The real work on the region side is behind the
picker: `RegionPreset` carries `displayName` and `page` only, with a doc
comment recording that richer fields were cut:

> Richer candidates (a document noun, a phone label, a date-style token)
> were cut because nothing downstream would actually read them.

That was the right call for UK/US, where the only real difference is A4
versus Letter. It stops being right the moment a third country arrives —
and the discipline in that comment is worth preserving rather than
overturning wholesale. This step adds only the fields that gain a
consumer, and explicitly defers the rest.

At 5–6 regions the *data* matters and the *picker* does not. At 10–15
templates it is the reverse: the picker is the whole problem and the
metadata behind it stays thin. Sizing each side to its own number is
most of this file.

This step depends on 7.4: the document bar is where both new pickers
live. Building them before it exists means building them twice.

---

## Decisions locked

| # | Decision | Rationale |
|---|---|---|
| 1 | Thumbnails are **rendered from the user's own data**, not shipped as static images | The existing pipeline already produces exactly this. Static previews of someone else's CV are less useful *and* rot when a template changes. |
| 2 | Thumbnail rendering is a new service, not a method on `PdfExportService` | Different concern (cached raster images for a picker vs. exportable bytes) and different lifetime. `stacked create service template_thumbnail`. |
| 3 | Cache keyed on `(templateId, ResolvedCv)` | `ResolvedCv` is `@freezed`, so it has real value equality and a stable `hashCode`. No revision counter needed and no risk of a stale thumbnail after an edit. |
| 4 | Add `tags` to `CvTemplate` now, while there are two implementations | Retrofitting an interface member across fifteen renderers is the expensive version of this. Two is cheap. |
| 5 | Tags **group** the gallery; they do not drive a filter control | Fifteen cards in three or four labelled groups is scannable in one pass. A filter widget over fifteen items is furniture that costs a click to reach the thing you could already see. |
| 6 | `RegionPreset` gains **only** `documentNoun` and `dateStyle` | Both have a consumer the moment they land. Photo/DOB expectations do not — see "Deferred" below. |
| 7 | `RegionProfile` stays an `enum`, settled | At 5–6 regions there is no scale argument against it at all, and persistence already keys on `.name`. This is no longer a "revisit later" decision. |
| 8 | Region picker is a plain `DropdownMenu`, **no `enableFilter`** | Six entries. Search over six items is worse than no search — it adds a keyboard interaction to a list you can read at a glance. The dropdown is chosen over keeping chips only because 7.4's document bar is one row and six chips will not fit it. |

## What changes

### New — `lib/services/template_thumbnail_service.dart`

```bash
stacked create service template_thumbnail
```

```dart
/// A rasterised first page per (template, content) pair, for the
/// template gallery. Renders through `PdfExportService.render` and
/// `Printing.raster` so a thumbnail can never show something the
/// exported PDF wouldn't — same bytes, same reasoning as
/// `CvTemplate`'s doc comment gives for the live preview.
Future<Uint8List> thumbnail({
  required ResolvedCv cv,
  required String templateId,
  required PdfPageFormat format,
});
```

`Printing.raster` is a `static Stream<PdfRaster>`
(`third_party/printing/lib/src/printing.dart:245`) — take the first
element, at a low `dpi` (roughly 40–50 is enough for a card-sized
thumbnail), and convert to PNG bytes.

Cache in a plain `Map`, keyed as decision 3. Bound it — one entry per
template is the natural cap since the `ResolvedCv` component of the key
invalidates on edit anyway, so evict any entry whose `cv` no longer
matches the current one rather than letting the map grow per keystroke.

Register it in the locator (the CLI does this) and add a
`getAndRegisterTemplateThumbnailService()` to
`test/helpers/test_helpers.dart` — the CLI scaffolds the mock spec, but
check the `// @stacked-mock-*` markers actually picked it up.

### `lib/templates/cv_template.dart`

```dart
/// Coarse classification for the gallery's filter, not a styling input
/// — no renderer reads this. Kept on the interface rather than in the
/// registry so a template and its own description of itself can't
/// drift.
Set<TemplateTag> get tags;
```

With a small enum alongside it — `atsSafe`, `academic`, `twoColumn`,
`compact`, `traditional`, `modern`. Both existing templates implement it
(two files, one line each). Do **not** add a `thumbnail` member: the
image is derived, not declared, and putting it on the interface would
mean every renderer carrying an asset.

### `lib/models/render/region_profile.dart`

```dart
class RegionPreset {
  const RegionPreset({
    required this.displayName,
    required this.page,
    required this.documentNoun,
    required this.dateStyle,
  });

  final String displayName;
  final PdfPageFormatToken page;

  /// "CV" or "Résumé" — what this region calls the document. Read by
  /// the chrome's own copy, never printed inside the document.
  final String documentNoun;

  final RegionDateStyle dateStyle;
}
```

Both new fields have a consumer immediately, which is the bar decision 5
sets:

- `documentNoun` fixes the review's wording finding — ATS Check says
  "Upload a PDF resume" while the rest of the app says CV. One of the
  two is wrong for any given user; this makes it right for both.
- `dateStyle` has a seam waiting for it. `CvComposer._formatDateRange`
  already takes `region` and already switches on it, with both branches
  currently identical:

  ```dart
  case RegionProfile.uk || RegionProfile.us:
  ```

  and a comment saying region stays threaded through as the seam. This
  is that seam being used for the first time — replace the switch on
  `RegionProfile` with a switch on `preset.dateStyle`, so adding a
  country stops requiring a composer change.

### The pickers, in `studio_document_bar.dart`

**Template** — replaces the chips with a button showing the current
template's name that opens a gallery dialog:

```bash
stacked create dialog template_gallery -c stacked_configs/studio.json
```

A responsive grid of cards: thumbnail, `displayName`, `description`,
tag chips, current one marked. Grouped under tag headings rather than
filtered (decision 5) — at fifteen templates that is three or four
labelled groups on one scrollable surface, and the user sees every
option without operating a control first. A template with several tags
files under its first; the rest still render as chips on the card.

Thumbnails render lazily per visible card and each needs a loading and a
failed state. The failed state matters: `PdfExportService.render` throws
a tagged `PdfExportException`, and a font-load failure under a deployed
`--base-href` would fail *every* thumbnail at once. Fall back to a
name-and-description card rather than an error grid — the gallery should
degrade to today's behaviour, not break.

**Region** — a plain `DropdownMenu` over `regionPresets`, no filtering.
Six entries fit in one menu without scrolling.

### Wording, once `documentNoun` lands

`analyzer_upload_prompt.dart`'s "Upload a PDF resume" becomes region-
aware, and the same pass should cap its message width — the review
measured it running to a single ~660px line, well past a comfortable
measure.

## Deferred, deliberately

`expectsPhoto`, `expectsDateOfBirth`, `phoneLabel`. Real regional
conventions — Germany and Japan expect a photo and a date of birth, the
US emphatically does not — and all three are unreadable today because no
template renders a photo or a DOB and `ContactBasics` has no field for
either. Adding them now recreates exactly the mistake `RegionPreset`'s
existing comment describes avoiding: fields nothing downstream reads.

They arrive with the first template that renders them, together with the
`ContactBasics` fields to hold the data. That is its own workstream and
a bigger one than this file — it touches the Vault editor, the composer,
`ResolvedCv`, and at least one renderer.

## Verification

```bash
stacked generate
dart format .
flutter analyze
flutter test --exclude-tags=golden
```

`stacked generate` is mandatory here, not optional — `RegionPreset` is
not `@freezed` but `test_helpers.dart` gains a mock, and the CLI's
locator/mock wiring runs through it.

**Service tests** — `test/services/template_registry_service_test.dart`
gains a `tags` assertion per template. New
`test/services/template_thumbnail_service_test.dart` covers: a
thumbnail is produced for a known template; the second call for the same
`(templateId, cv)` does not re-render (assert via the mocked
`PdfExportService` call count — this is the cache's whole contract); a
different `cv` does re-render; a `PdfExportException` propagates rather
than returning empty bytes.

**Composer tests** — the date-style switch is a behaviour change even
though both current styles are identical. Assert that a UK draft and a
US draft each produce their expected `dateRange` string, so the seam has
coverage before a third style arrives.

**Goldens** — `settings_view_default.png` and the two `drafts_list_view`
baselines are unaffected. `vault_view_*` are unaffected. Nothing here
touches `AppChrome` or the theme. But `test_helpers.dart`'s
`getAndRegisterTemplateRegistryService()` stubs against **real**
`CompactTemplate()`/`ClassicCenteredTemplate()` instances, so adding an
interface member that those two must implement will break compilation of
every golden test until they do. Expect that, and do not mistake it for
a baseline change.

**Browser** — open the gallery with the example vault: thumbnails show
the user's actual CV, differ visibly between the two templates, and the
current template is marked. Switch template from the gallery and confirm
the preview updates. Switch region and confirm both the page format
(7.3's cap should change with it) and the document noun in ATS Check's
copy. Then reload and confirm both persisted.

## Risks

1. **Thumbnail rendering cost on open.** Fifteen templates is fifteen
   full PDF renders plus fifteen rasters. Rendering is fast (tens of ms,
   measured per `StudioPreviewPane`'s debounce comment) but fifteen of
   them at once on the main isolate will be felt, and unlike the preview
   there is nothing to debounce against — they all want to appear now.
   Render lazily per visible card, accept a progressive fill, and keep
   the cache across gallery opens so the second visit is instant. This
   is the one risk here that grows with the template count rather than
   staying flat.
2. **Cache key on `ResolvedCv.hashCode`.** Value equality on a `@freezed`
   class with nested lists is correct but the hash is computed over the
   whole graph on every lookup. For a large CV in a picker this is fine;
   if the map is ever consulted per frame it will not be. Keep lookups
   to gallery-open, not build.
3. **`tags` growing into styling.** Decision 4's doc comment exists to
   prevent a renderer reading `tags` and branching on it. If that
   happens the tag has become a token and belongs in `CvDesignTokens`.
4. **Tags becoming a taxonomy.** With grouping rather than filtering,
   the tag set is now load-bearing for layout — a template with no tag
   has nowhere to go, and fifteen templates across ten tags is fifteen
   groups of one. Keep the enum small (four or five values) and require
   every template to declare at least one.

## Not in scope

Photo and date-of-birth support; new templates themselves (this step
makes room for them); localisation of the app's own UI, which is a
different problem from regional document conventions and should not be
conflated with it.
