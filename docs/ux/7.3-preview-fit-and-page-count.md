# 7.3 — Preview fit and page count

## Context

Two findings, one widget.

**The preview scales to fill, not to fit.** `StudioPreviewPane` passes no
`maxPageWidth`, so the page sizes itself to the pane. Measured in the
browser at a 1728px viewport, the config panel takes ~553px and the
preview pane ~1140px, which renders A4 at roughly 1,050px — about 130%
of its printed size. You see a zoomed-in fragment of page one. On a
3440px display it gets worse, not better, because the pane grows and the
page grows with it.

**Page count appears nowhere in the app.** For a CV this is the single
most load-bearing number there is — one page or two is a decision
recruiters act on — and the UI never states it. `PdfPreview` runs with
`useActions: false`, so there is also no zoom control and no page
indicator. Scrolling the preview reveals a page break with nothing
labelling it.

Both are cheap to fix, and the investigation turned up a third thing
that makes them cheaper still.

---

## What the vendored source actually offers

`printing` is not a plain hosted dependency here — `pubspec.yaml` has a
`dependency_overrides` entry pointing at `third_party/printing`, a
locally-patched copy of 5.15.0. So the API surface is readable, and
patchable if it comes to that. It does not come to that.

Confirmed by reading `third_party/printing/lib/src/preview/`:

- `PdfPreview` accepts `maxPageWidth` (`pdf_preview.dart:41`) and
  forwards it, along with `onError`, `loadingWidget` and `dpi`, straight
  down to `PdfPreviewCustom` (lines 412–423).
- `PdfPreviewCustom` (`custom.dart:35`) accepts everything
  `StudioPreviewPane` currently uses — `build`, `onError`,
  `shouldRepaint`, `loadingWidget`, `maxPageWidth`, `dpi` — **plus**
  `pagesBuilder`, typed `CustomPdfPagesBuilder = Widget Function(
  BuildContext, List<PdfPreviewPageData>)` (`custom.dart:32`).
- `PdfPreview` does **not** expose `pagesBuilder`. Only the inner widget
  does.

The consequence is the useful part. `StudioPreviewPane` currently passes
`useActions: false`, `canChangePageFormat: false` and
`canChangeOrientation: false` — three arguments whose only job is to
switch off `PdfPreview`'s action bar, which is the entire reason
`PdfPreview` exists as a wrapper. **It has been using the wrapper with
the wrapper's purpose disabled.** Moving to `PdfPreviewCustom` deletes
those three arguments, keeps every other one unchanged, and hands us the
page list.

No patch to the vendored package is needed. That was the assumption
going in and it turned out to be wrong in our favour.

---

## Decisions locked

| # | Decision | Rationale |
|---|---|---|
| 1 | Swap `PdfPreview` → `PdfPreviewCustom` | Confirmed drop-in for every argument in use; removes three no-op flags; is the only widget exposing `pagesBuilder`. |
| 2 | Cap the page at its true printed width via `maxPageWidth` | One-line fix for the over-scale, and it is the package's own intended mechanism rather than a wrapper of ours. |
| 3 | Derive the cap from `PdfPageFormat`, never a literal | The cap differs between A4 and Letter, and region switching already changes `pageFormat`. A hardcoded 794 silently mis-sizes US drafts. |
| 4 | Page count comes from `pagesBuilder`'s list, not by parsing PDF bytes | The rasterisation already happens; counting its output is free. Parsing bytes or calling `Printing.raster` again would rasterise twice. |
| 5 | Two-up spread is **width-gated, not a user toggle** | It is a consequence of available width, like the existing desktop/compact split. A toggle would be a third piece of state to persist for no decision the user actually wants to make. |
| 6 | Export stays a FAB in this step | It belongs in 7.4's document bar. Moving it here means moving it twice. |

## What changes

### `lib/features/studio/widgets/studio_preview_pane.dart`

The whole change lives in this file plus one getter on the ViewModel.

**The width cap.** `PdfPageFormat.width` is in PDF points and
`PdfPageFormat.inch` is 72.0, so a page's printed width in CSS pixels is
`format.width / PdfPageFormat.inch * 96`. For A4 that is 793.7px; for
Letter, 816px. Express it as a named constant with the derivation in the
comment — the 96 is the CSS reference pixel, not a measured property of
the user's display, and the next person to read it will want to know
that we know.

```dart
/// A CV is a printed artefact, so the preview should never render the
/// page larger than its printed size — scaling past 100% shows a
/// zoomed fragment and answers none of the questions ("does it fit on
/// two pages", "how does the whole page look") the preview exists for.
/// 96 is the CSS reference pixel per inch, not the display's real DPI,
/// which the web cannot know.
double _printedWidth(PdfPageFormat format) =>
    format.width / PdfPageFormat.inch * 96;
```

**Page count.** Supply `pagesBuilder` and read `pages.length`. The
builder is responsible for laying the pages out, so it is also where the
two-up spread happens — one builder, both features.

Surfacing the count needs care about *where*: a `setState` from inside
`pagesBuilder` during build is a loop. Hold the count in the pane's own
`State` and update it via `WidgetsBinding.instance.addPostFrameCallback`
guarded on a real change, or lift it to the ViewModel the same way. The
former keeps a presentation concern out of the ViewModel; the latter is
needed if 7.4's document bar is to show it. **Prefer the ViewModel**,
because 7.4 will want it in the bar and moving it later means doing this
twice — see risk 2 on the notify-during-build hazard.

**Two-up.** Gate on the pane's own constraints, not the window:
`LayoutBuilder`, and go two-up when
`constraints.maxWidth >= printedWidth * 2 + gutter`. At A4 that is
~1,620px of pane, which a 1728px window does not reach once the config
panel takes its share — so on today's layout two-up appears only on
genuinely wide displays. That is correct behaviour, but it does mean
**the feature is untestable on a 1600px screen**; verify it by narrowing
the config panel temporarily or on the real 3440px display.

### `lib/features/studio/views/studio/studio_viewmodel.dart`

```dart
/// Page count of the most recent successful render, or null before the
/// first one. Set by `StudioPreviewPane`, which is the only place the
/// rasterised page list exists.
int? get pageCount;
void setPageCount(int value);
```

A setter called only by a widget is close to `CLAUDE.md`'s "no
production API that only tests call" smell, but it is the inverse case —
a real call site exists and the value has a real consumer. Worth a doc
comment saying which widget owns it so it does not read as orphaned.

**Where it is displayed:** a caption in the preview pane for now
("Page 1 of 2" style, or simply "2 pages"), relocating to the document
bar in 7.4. Do not build a page navigator — `enableScrollToPage` exists
on `PdfPreviewCustom` if that is ever wanted, and scrolling already
works.

## Steps

1. Add `maxPageWidth`. Verify in the browser at 1728px that the page
   stops growing and now sits at printed size with the backdrop visible
   around it. This alone is worth shipping and is one line.
2. Swap to `PdfPreviewCustom`, deleting `useActions`,
   `canChangePageFormat`, `canChangeOrientation`. Confirm the error path
   still renders `_buildPreviewError` — `onError` is forwarded, but
   confirm it rather than trust the forwarding.
3. Re-verify the debounce and repaint gate (see risk 1) before adding
   anything else.
4. Add `pagesBuilder`, the page count, and its display.
5. Add the two-up branch.

Steps 1–3 are the valuable part. If 4 or 5 turn awkward, they can be
dropped without losing the fix.


`test/services/pdf_export_service_test.dart` covers rendering and
pagination and should be untouched by this — it exercises
`PdfExportService.render` directly, not the preview widget. If it moves,
something has gone wrong in the wrong layer.

**Goldens.** None. There is no golden for `StudioView`, confirmed
against `test/golden/`. Nothing here is pixel-covered by tests, which
makes the browser pass below the only real verification.

**Browser**, at three widths, with the example vault loaded:

- **1728px** — page renders at printed size, not blown up; whole page
  width visible with backdrop either side; page count shown and correct
  against a manual scroll; scrolling still reaches page 2.
- **~1000px** — page shrinks to fit the narrower pane (the cap is a
  maximum, not a fixed size); nothing clips.
- **Compact/tabbed** — the Preview tab still renders; the cap does not
  leave a tiny page in a wide-ish tab.

Then switch region UK → US and confirm the cap changes with the format
rather than staying at A4's value. That is decision 3's whole point and
it is the easiest thing here to get wrong invisibly.

Finally, edit a bullet and confirm the preview still updates once, after
the debounce, and does not re-render in a loop.

## Risks

1. **The repaint gate.** `_buildPdf` is deliberately a bound method, not
   a closure, because `PdfPreview` regenerates when the callback's
   *identity* changes — a fresh closure per rebuild causes runaway
   regeneration, and each regenerate's `setState` feeds the next. The
   existing doc comment spells this out. `PdfPreviewCustom` takes the
   same `build` callback and the same `shouldRepaint`, so the contract
   should be identical — **inferred, not confirmed.** Phase 6.1 already
   recorded a `StudioPreviewPane` repaint-gate regression that the test
   suite did not catch, so verify by watching for repeated renders after
   a single edit rather than assuming.
2. **Notifying during build.** `pagesBuilder` runs inside build. Calling
   a ViewModel setter that notifies listeners from there will assert or
   loop. Post-frame callback, guarded on the value actually changing.
3. **`shrinkWrap` and `scrollPhysics` defaults.** `PdfPreviewCustom`
   defaults `shrinkWrap: false`, which `PdfPreview` may have been
   setting differently for its own layout. If the preview ends up with
   unbounded-height or double-scroll trouble after the swap, this is the
   first place to look.

## Not in scope

Zoom controls, a page navigator, print (as opposed to export), and
moving Export into a document bar. The last one is 7.4.
