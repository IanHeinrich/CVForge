# 7.8 — Vault

## Context

The Vault is in better shape than Studio — the master–detail split
works, the editor panel is the best-composed surface in the app, and
`VaultListSection<T>` is a clean generic. 7.4 explicitly proposes
copying its layout.

But it holds a **data-loss bug in the date fields**, and a destructive
action in the worst possible place, and neither showed up in the
original review because both need the code read rather than the screen
looked at.

---

## Decisions locked

| # | Decision | Rationale |
|---|---|---|
| 1 | Fix the date entry as a **correctness** fix, not a polish one | It silently diverges the UI from the model and can persist a wrong value. See below. |
| 2 | Replace month text entry with a month `DropdownButtonFormField` | Twelve fixed options. `YearMonth` already carries the twelve names in `_monthNames`; a free-text field over a closed set is the wrong control regardless of the bug. |
| 3 | Move "Clear Vault" out of the Vault and into Settings | It is a destructive whole-dataset action currently rendered above the user's own name, and it belongs next to Backup, where the export-first reasoning already lives. |
| 4 | Cap the card list's content width | Same finding as everywhere else: a Vault row is currently a 1,500px bar holding two short lines with its delete icon a screen-width away from the label it deletes. |
| 5 | **Do not** unify `_BasicsCard`/`_SkillsCard`/`_HobbiesCard` with `VaultListSection` | They are genuinely different — a singleton that opens an editor versus a collection with per-item add/delete. The inconsistency is in the *subtitles*, not the structure. See below. |

## The date bug

`experience_editor_panel.dart`, start month (end month is identical):

```dart
AppTextField(
  label: 'Start month',
  initialValue: experience.start.month.toString(),
  keyboardType: TextInputType.number,
  onChanged: (v) {
    final month = int.tryParse(v);
    if (month != null && month >= 1 && month <= 12) {
      onChanged(experience.copyWith(
        start: experience.start.copyWith(month: month)));
    }
  },
),
```

Invalid input takes the `if` and falls out of the function. No write, no
error, no signal. Combined with `AppTextField`'s behaviour — a 400ms
debounce, and a `didUpdateWidget` that only resyncs `_controller.text`
from `initialValue` **when the field is unfocused** — this produces
three distinct failures. All derived from source; synthetic keyboard
input would not reach the Flutter canvas in the preview browser, so
none were reproduced live.

**1. Silent divergence, persisting indefinitely.** Type `13`. The guard
rejects it, so the model keeps `9`. The field still reads `13`. On blur,
`_flush()` re-sends `13` and it is rejected again. The model never
changed, so nothing notifies, so the parent never rebuilds, so
`didUpdateWidget` never fires and never resyncs. **The field shows 13
and the data is 9, with no error, until something unrelated triggers a
rebuild.** Clearing the field to empty does the same thing.

**2. A transient wrong value that can persist.** Changing `9` to `10`
means select-all then type `1`, `0`. After `1` the debounce fires and
writes **month = 1 — January** — a valid value, so it goes all the way
through `VaultService` to storage. Typing `0` corrects it to `10`. But
pause longer than 400ms mid-edit, or tab away after `1`, and January is
what was saved and what the field will show.

**3. End-month seeds from start.** `final end = experience.end ??
experience.start;` — setting an end month on an entry with no end date
silently adopts the **start year** as the end year until the year field
is also set. Plausible values, wrong data.

### The fix

A month dropdown removes failures 1 and 2 entirely: a closed set has no
invalid state to reject and no partial-entry keystroke to write. Use
`YearMonth`'s existing `_monthNames` (promote it out of private, or add
a `monthName(int)` helper next to `toMonYyyy()` so the list has one
owner).

Year stays a text field — it is genuinely free-form — but needs the
`errorText` that 7.7 adds to `AppTextField`, plus a sane range check.
The rule for both, and this is the part worth writing down: **a
rejected edit must either show an error or be impossible to make.**
Silently discarding it is the one option that is not allowed.

Failure 3 is separate: an entry with no end date should require the
year before the month means anything, or should default the year to the
current year rather than the start's. Either is defensible; the current
behaviour is not.

The same pattern appears in `education_editor_panel.dart` and anywhere
else taking a `YearMonth` — check all of them, not just experience.

## "Clear Vault"

`vault_card_list.dart` renders it as the first item in the list, in an
`Align(centerRight)`, above the basics card:

```dart
Align(
  alignment: Alignment.centerRight,
  child: TextButton.icon(
    onPressed: viewModel.clearVault,
    ...
```

Three things wrong. It is the **first interactive element on the
screen**, above the user's own name. It is a `TextButton` — the same
visual weight as "Add experience" — distinguished only by being red. And
on a wide display the `Align(centerRight)` throws it to the far right
edge, ~1,500px from anything it relates to.

It does go through a confirm dialog, which is the only reason this is a
placement problem rather than an incident waiting to happen. Move it to
Settings beside Backup, where "export first, then restore replaces
everything" is already the established framing, and where a destructive
action is expected to live.

## The subtitle inconsistency

Decision 5 says the two card shapes are fine. What is not fine is what
they put in the subtitle.

`_SkillsCard` summarises well — "3 categories, 11 skills". `_HobbiesCard`
joins **every** hobby with `", "` into a subtitle that `AppSummaryCard`
then truncates at `maxLines: 1`. With more than about four hobbies you
get "Running, Chess, Photography, Cook…" — a summary that has stopped
summarising and become a truncated list. Give it a count, like Skills.

Worth a general pass: `AppSummaryCard` truncates title, subtitle and
notes to one line each, so any caller building a subtitle by joining a
collection is producing that same effect. `_HobbiesCard` is the only
current offender.

## Also

- **No search, no section collapse, no jump.** Same finding as Studio.
  Sections are hardcoded in one order, always expanded, so with fifteen
  jobs the Publications section is a long way down. Least urgent of the
  layout items, but it is the same missing capability and should be
  solved once, not twice.
- **Unverified:** loading the example vault from the empty state
  appeared not to repaint until a manual reload. This may simply be
  screenshot timing — the click and the capture were back to back with
  no frame in between. Worth ten seconds to check whether
  `loadExampleVault` notifies; if it does not, the empty state can sit
  there after a successful load.

## Verification

```bash
stacked generate
dart format .
flutter analyze
flutter test --exclude-tags=golden
```

**ViewModel tests** — `test/features/vault/viewmodels/vault_viewmodel_test.dart`
already covers experience CRUD and `clearVault`. The date fix is mostly
widget-level, but the behaviour worth asserting at the ViewModel is
`updateExperience` with an out-of-range month: it should be
unreachable once the dropdown lands, and a test saying so documents the
invariant.

`clearVault` moving surface does not change its ViewModel test — but
check whether `VaultViewModel` is still where it belongs once the
trigger lives in Settings, or whether `SettingsViewModel` should own it.

**Goldens** — `vault_view_empty.png` and `vault_view_populated.png` both
change: Clear Vault leaving the list, the width cap, and the hobbies
subtitle all land in the populated baseline. Two of the five. Dispatch
`update-goldens.yml` and commit in the same PR.

**Browser** — the date fields are the point of this file, so exercise
them directly: set a month via the dropdown and confirm the preview and
the summary card update; set an invalid year and confirm an error
appears rather than the value silently vanishing; set an end month on an
entry with no end date and confirm the year behaves as decided rather
than adopting the start's.

Then reopen the panel after each edit and confirm the field shows what
was actually saved — that round trip is exactly the one the current
implementation fails.

## Risks

1. **`AppTextField.errorText` needs a validation home.** Adding the
   parameter is trivial; deciding *where* validation lives is not. The
   panel is a `StatelessWidget` taking callbacks, so per-field error
   state has nowhere to sit without making it stateful or pushing
   validation into `VaultViewModel`. Prefer the ViewModel — it matches
   `CLAUDE.md`'s "logic in the ViewModel" rule and keeps the panel
   declarative — but it means a validation-error map on the ViewModel,
   which is a real design decision, not a detail.
2. **Month dropdown in a `Row` with year.** The existing layout is two
   `Expanded` text fields. A dropdown and a text field with different
   intrinsic heights in one row will need alignment attention,
   especially once `errorText` makes the year field taller when invalid.
3. **Existing bad data.** If failure 2 has already written a wrong month
   into anyone's stored Vault, the fix does not repair it — it only
   stops new occurrences. Worth checking the example vault and any real
   data for implausible dates before assuming the fix is complete.
