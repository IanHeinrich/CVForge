# 7.2 — Grouped chip skill selection

## Context

Studio selects skills with one full-width `CheckboxListTile` per skill,
and flattens the categories away first:

```dart
// studio_config_panel.dart
for (final category in viewModel.skillCategories)
  for (final skill in category.skills)
    SelectorItem(
      title: skill.label,
      subtitle: category.name,   // repeated on every row
      ...
    )
```

Three separate problems, in increasing order of seriousness.

**It is the wrong control for the cardinality.** Each row is a
two-line tile in a column clamped to 380–676px. Eleven sample skills is
merely wasteful; a realistic sixty is roughly 2,900px of scrolling with
the category name printed sixty times.

**It contradicts the output.** `CvComposer._buildSkills` groups
selected skills back into `ResolvedSkillGroup(category:, skills:)`, and
both templates print those category names as real structure
("Languages & Frameworks:", "Cloud, DevOps & AI:"). The selector
discards the exact grouping the document then reinstates, so the control
and the artefact disagree about what a skill list is.

**There is no way to find anything.** Confirmed by grep: no search or
filter field exists anywhere in the application.

The correct control is already written in this repo.
`skills_editor_panel.dart`'s `_SkillBulletLinkPicker` uses a `Wrap` of
compact `FilterChip`s under per-group headings — multi-select, many per
row, group name shown once. It is in the Vault and never made it to the
Studio.

---

## Decisions locked

| # | Decision | Rationale |
|---|---|---|
| 1 | Extract the `Wrap` + `FilterChip` pattern into a shared widget in `lib/ui/widgets/common/` | It will have two consumers in two features (Vault's bullet-link picker, Studio's skill selector), which is exactly `CLAUDE.md`'s bar for shared UI. Below two consumers it should have stayed put. |
| 2 | Scaffold it with `stacked create widget … --no-model` | Hard rule in `CLAUDE.md`. `--no-model` because it is a pure presentational widget with no state beyond what the caller owns — a `WidgetModel` here would be an empty class. |
| 3 | Keep categories as headings; **do not** invent a flat "all skills" mode | The document groups by category. A selector that can disagree with the document is the bug being fixed. |
| 4 | Filter text is widget-local `State`, not ViewModel state | Presentation state, not draft data — same call as `_expandedIds`/`_editingTextIds` in `vault_item_selector_list.dart`, and it should not persist or survive a rebuild of the draft. |
| 5 | Per-category bulk select gets its own ViewModel method | It must await each toggle sequentially. See risk 1 — this is a known, already-documented hazard in this codebase, not a theoretical one. |
| 6 | "Select skills your bullets prove" ships **in this file**, not deferred | It is the same surface, the same session, and the data has been sitting unused since Phase 1. Splitting it means touching the same widget twice. |
| 7 | No line-count estimate in the budget cue | Honest line count needs the rendered PDF. Show the counts we actually know and let the preview answer the rest — see "Rejected" below. |

## What changes

### New — `lib/ui/widgets/common/app_chip_group_selector.dart`

```bash
stacked create widget app_chip_group_selector --no-model
```

Presentational, stateless, no `ViewModel` dependency. Takes a list of
groups, each with a label and a list of items carrying `id`, `label`,
`selected`, `onToggle`, plus an optional `onSelectAll`/`onSelectNone` per
group and an optional `tooltip` per item (the Vault's bullet picker needs
tooltips; skills do not).

Reuse `context.appSpacing`/`appTypography` for spacing and the group
heading, and `visualDensity: VisualDensity.compact` on the chips, exactly
as `_SkillBulletLinkPicker` already does — the point of the extraction is
that the two surfaces stop being able to drift.

### `lib/features/vault/widgets/skills_editor_panel.dart`

Replace `_SkillBulletLinkPicker`'s inner `Wrap` with the new widget.
Keep the expand/collapse affordance and the "Linked to N bullets" label
— those are specific to that panel and are not part of the shared piece.

This step is what proves the extraction is honest: if the shared widget
cannot serve the surface it was extracted from, it is the wrong shape.

### `lib/features/studio/widgets/studio_skill_selector.dart` — new

```bash
stacked create widget studio_skill_selector --no-model \
  -c stacked_configs/studio.json
```

Owns the filter `TextField` (local `State`), then renders
`AppChipGroupSelector` over `viewModel.skillCategories`, filtered.

Behaviour worth pinning down now rather than discovering later:

- Filtering matches on skill label **and** category name, case-
  insensitively. Typing "cloud" should surface the whole Cloud category,
  not nothing.
- A group whose skills are all filtered out disappears, heading
  included.
- **A selected skill filtered out of view stays selected.** Filtering is
  a view over the set, never a mutation of it. Worth a ViewModel test.
- The header line shows `N of M selected` plus the per-category
  all/none affordance, matching the existing "Add all (N)" wording used
  everywhere else in Studio rather than inventing "Select all".

### `studio_config_panel.dart`

Delete the `VaultItemSelectorList(title: 'Skills', …)` block and call
`StudioSkillSelector` instead. This is the only skills-related change to
this file; the rest of its restructuring is 7.4's problem.

### `studio_viewmodel.dart` — three additions

Near the existing `// --- skills ---` block (lines 515–537, which
already holds `_skillSelection`, `isSkillIncluded`, `toggleSkill`,
`unselectedSkills`, `addAllSkills`):

```dart
Future<void> addAllSkillsInCategory(SkillCategory category);
Future<void> removeAllSkillsInCategory(SkillCategory category);

/// Selects every skill whose `linkedBulletIds` intersects the set of
/// bullets currently included in this draft — never deselects.
Future<void> selectEvidencedSkills();
```

`selectEvidencedSkills` needs the included-bullet-id set, which is the
union of the values of `CvDraft.bulletIds`, `projectBulletIds` and
`publicationBulletIds`, restricted to entries that are themselves
included. That is a private getter on the ViewModel; it does not belong
on `CvDraft`, which should stay a dumb data holder.

All three must reuse the sequential-await shape of `_Selection.addAll`.

## The unplugged feature

`Skill.linkedBulletIds` records which bullets demonstrate each skill.
The Vault has complete UI for setting those links. Nothing reads them —
the model's own doc comment says so:

> Purely descriptive metadata in Phase 1 — the composer/template don't
> read it.

In Studio that is one button: **"Select the skills your bullets prove"**.
It only claims what the CV actually evidences, it is one click instead of
sixty, and it is not copyable by a competitor without the same model.

Two constraints on the copy and the behaviour, both worth getting right
first time:

- It **adds** only. A skill selected manually and not linked to any
  included bullet must survive the action, or the button becomes
  destructive and needs a confirm.
- Show the count before acting, not a silent mutation — the label can
  carry it (`Select 14 evidenced skills`), which also disables cleanly
  when the count is zero.

---

## Rejected

**A line-count budget cue** ("14 selected · about 3 lines"). It reads
well and it would be a lie: true line count depends on the template's
font metrics, the page width, and the category label lengths, none of
which the selector can see. The preview already answers the question
truthfully, and 7.3 makes it answer faster. Ship `N of M selected` and
leave it there.

**Search across the whole Studio panel.** Tempting while the filter
plumbing is fresh, but the panel is about to be restructured by 7.4 and
a global search belongs in the document bar that step introduces.
Skills-only now; generalise once there is somewhere for it to live.

## Verification

```bash
stacked generate
dart format .
flutter analyze
flutter test --exclude-tags=golden
```

**ViewModel tests** — extend
`test/features/studio/viewmodels/studio_viewmodel_selection_test.dart`,
which already covers the per-item toggles and `addAll*` for every other
category. Outside-in through the public API, per `CLAUDE.md`; mock
services via `registerServices()`. Cover:

- `addAllSkillsInCategory` selects only that category's skills and
  leaves other categories untouched.
- `removeAllSkillsInCategory` is its inverse and does not disturb
  manual selections elsewhere.
- `selectEvidencedSkills` selects a skill linked to an included bullet,
  does **not** select one linked only to an excluded bullet, and does
  not deselect a manually-selected unlinked skill.
- Sequential-await correctness: after `addAllSkillsInCategory` on a
  category of three, all three ids are in `draft.skillIds` — the
  assertion that catches risk 1.

**Goldens.** None affected. There is no golden for `StudioView` or for
any `lib/features/studio/widgets/` widget, and Phase 3.8 already
recorded that the Vault skills panel does not render in either
golden-tested View's default state. Confirmed, not assumed.

**Browser.** This one needs eyes, because nothing above tests pixels.
Load the example vault, open Studio, and check: sixty-odd chips fit
without scrolling where sixty rows did not; category headings appear
once each; typing in the filter narrows both by skill and by category;
clearing the filter restores selections intact; the evidenced-skills
button selects a plausible set and its count matches what it selects.

## Risks

1. **Stale-draft writes on bulk select.** `_Selection.addAll` and
   `SelectorItem.onAddAllBullets` both carry doc comments warning that
   firing every toggle synchronously makes them all read the same stale
   draft so only the last lands. Any new bulk method repeats the bug if
   it does not await sequentially. The test above is the guard.
2. **Chip target size.** `VisualDensity.compact` on sixty chips is
   dense; the Vault picker gets away with it on a handful. If chips end
   up under ~32px tall, back the density off rather than keeping the
   density and losing the tap target.
3. **The extraction going one consumer too early.** If the Vault's
   bullet picker needs three parameters the skill selector never uses,
   the shared widget is accreting rather than sharing. Two consumers is
   the bar; if it starts wanting a fourth optional flag, split it back
   apart.

## Not in scope

Reordering skills or categories, editing skills from Studio (the Vault
owns that), and making the composer read `linkedBulletIds` for anything
other than this selection helper.
